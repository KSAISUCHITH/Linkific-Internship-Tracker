## Overview

BookNest lets users browse a catalogue of books, mark favorites, rate books, and manage a personal library. Administrators additionally manage the catalogue itself (create, update, delete books).

The project is split into two independently run applications:

| Part | Location | Description |
|------|----------|-------------|
| Backend | `backend/` | FastAPI REST API, authentication, business logic, PostgreSQL access |
| Frontend | `frontend/frontend/` | React + Vite single-page application styled with Tailwind CSS |

---

## Features

**Accounts and security**
- User registration and login
- JWT access-token authentication (`Authorization: Bearer <token>`)
- Password hashing with bcrypt (via Passlib)
- Authentication persistence on the client and logout
- Protected routes on the frontend
- Role-based authorization with administrator users

**Books**
- Book listing and individual book details
- Admin-only book creation, update and deletion
- New releases view

**Per-user data**
- User-specific favorites
- User-specific ratings, with rating validation
- Personal library: borrow and return books (and download-related library functionality)

**Quality**
- Frontend input validation (`validation.jsx`) and backend validation (Pydantic schemas)
- Structured API error responses
- PostgreSQL persistence through SQLAlchemy
- Interactive API docs generated by FastAPI

## Architecture

```text
   User (Browser)
        |
        v
+--------------------+
|  React Frontend    |   Vite dev server, Tailwind CSS
|  (pages, components|
|   + api.js / Axios)|
+--------------------+
        |
        |  HTTP / JSON
        |  Authorization: Bearer <access_token>
        v
+--------------------+
|  FastAPI Backend   |   Uvicorn, Pydantic validation,
|  (main.py, auth.py,|   JWT auth, role checks
|   crud.py)         |
+--------------------+
        |
        |  SQLAlchemy ORM
        v
+--------------------+
|  PostgreSQL        |
+--------------------+
```

| Layer | Role |
|-------|------|
| **React** | Renders pages and reusable components, manages client-side routing and auth state. |
| **API layer (`api.js`)** | Central Axios-based module through which the frontend calls the backend. |
| **FastAPI** | Defines HTTP endpoints, validates requests/responses with Pydantic, enforces authentication and authorization. |
| **SQLAlchemy** | Maps Python models to PostgreSQL tables and executes queries (data-access logic lives in `crud.py`). |
| **PostgreSQL** | Persistent storage for users, books, favorites, ratings and library entries. |
| **JWT authentication** | Stateless access tokens issued at login and sent with each protected request. |

## Environment Variables

The backend reads its configuration from a `.env` file in `backend/`. Use `.env.example` as the template.

| Variable | Purpose | Example |
|----------|---------|---------|
| `DATABASE_URL` | SQLAlchemy connection string for PostgreSQL | `postgresql+psycopg://postgres:YOUR_PASSWORD@localhost:5433/book_next_2` |
| `FRONTEND_URL` | Frontend origin allowed by CORS | `http://localhost:5173` |
| `SECRET_KEY` | Secret used to sign JWTs | `your-development-secret` |

```env
DATABASE_URL=postgresql+psycopg://postgres:YOUR_PASSWORD@localhost:5433/book_next_2
FRONTEND_URL=http://localhost:5173
SECRET_KEY=your-development-secret
```

> [!IMPORTANT]
> - **Never commit `.env`** to GitHub.
> - **Never expose production secrets.** Generate a long random `SECRET_KEY` for any non-local use (for example `python -c "import secrets; print(secrets.token_urlsafe(48))"`).
> - Use `.env.example` as a template and replace placeholder credentials with your own local values.

## Docker

The **backend** is containerized. The frontend and PostgreSQL are **not** containerized, there is **no Docker Compose setup**, and BookNest has **not** been deployed to any cloud or production environment. Docker here provides a consistent backend runtime and a foundation for future deployment.

### Why Docker

A container packages the backend together with its exact Python version and dependencies, so it runs the same way on any machine with Docker installed.

### The Dockerfile

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . /app

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

| Instruction | What it does |
|-------------|--------------|
| `FROM python:3.12-slim` | Starts from a small official Python 3.12 image |
| `WORKDIR /app` | Sets the working directory inside the image |
| `COPY requirements.txt .` + `RUN pip install ...` | Installs dependencies first so Docker can cache this layer |
| `COPY . /app` | Copies the backend source into the image |
| `EXPOSE 8000` | Documents that the app listens on port 8000 inside the container |
| `CMD [...]` | Starts Uvicorn, listening on all interfaces |

The `.dockerignore` excludes files such as `venv/`, `__pycache__/`, `*.pyc`, `.env` and `.git/` from the build. Because `.env` is excluded, **secrets are never baked into the image** and must be supplied at runtime.

### Image vs. container

An **image** is a read-only template built from the Dockerfile. A **container** is a running instance of that image.

### Build and run

```bash
cd backend
docker build -t fastapi .
docker run -p 8080:8000 --env-file .env fastapi
```

- `-p 8080:8000` maps port **8080** on your machine to port **8000** in the container.
- `--env-file .env` passes `DATABASE_URL`, `FRONTEND_URL` and `SECRET_KEY` to the container at runtime.
- Swagger UI is then available at **http://localhost:8080/docs**.

Without `--env-file`, the container starts without the configuration the app needs, so database access will fail.

### PostgreSQL connectivity

PostgreSQL runs on the host, outside Docker. Inside a container, `localhost` refers to the container itself, not your machine. In `DATABASE_URL`, use a host address the container can reach, for example `host.docker.internal` on Docker Desktop (Windows/macOS):

```env
DATABASE_URL=postgresql+psycopg://postgres:YOUR_PASSWORD@host.docker.internal:5433/book_next_2
```

Also make sure PostgreSQL accepts connections from Docker's network. On Linux, additional configuration (such as `--add-host=host.docker.internal:host-gateway`) may be needed.

If the frontend runs on Vite's default port, keep `FRONTEND_URL=http://localhost:5173` so CORS continues to work.

### Authentication APIs

#### POST `/auth/register`

**Purpose:** Create a new BookNest user account.

**Authentication:** Not required.

**Request body:**

```json
{
  "name": "Asha Rao",
  "email": "asha@example.com",
  "password": "Password@123"
}
```

**Example request:**

```bash
curl -X POST http://localhost:8000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name":"Asha Rao","email":"asha@example.com","password":"Password@123"}'
```

**Successful response (`201 Created`):**

```json
{
  "id": 1,
  "name": "Asha Rao",
  "email": "asha@example.com"
}
```

**Errors:** `400` (e.g. email already registered), `422` (validation failed).

## Authentication and Authorization

These two ideas are related but different:

| | Authentication | Authorization |
|--|----------------|---------------|
| **Question** | *Who are you?* | *What are you allowed to do?* |
| **BookNest example** | Logging in with email and password proves you are a specific user and yields a JWT. | Only an administrator may create, update or delete books, while any logged-in user may manage their own favorites and ratings. |
| **Failure code** | `401 Unauthorized` | `403 Forbidden` |

### How it works

1. **Register:** the password is hashed with bcrypt before it is stored; the plain password is never saved.
2. **Login:** the backend finds the user, verifies the password against the stored hash, and creates a signed JWT access token (using `SECRET_KEY`).
3. **Authenticated requests:** the frontend sends the token in the `Authorization` header:

   ```http
   Authorization: Bearer <access_token>
   ```

4. **Identifying the user:** a FastAPI dependency (in `dependencies.py`) decodes and validates the token and loads the current user from the database.
5. **Authorization:** admin-only endpoints additionally check that the current user has administrator privileges; otherwise the API responds with `403`.
6. **Client side:** the frontend persists the session, attaches the token to API calls, protects routes that require login, and clears the token on logout.

> The secret key is only ever read from the environment. Do not hard-code it.

## Database Overview

BookNest uses PostgreSQL through SQLAlchemy. Models are defined in `backend/models.py`.

| Entity | Purpose |
|--------|---------|
| **User** | A registered account: credentials (hashed password), identity and role (regular user or administrator) |
| **Book** | A catalogue entry managed by administrators |
| **Favorite** | Links a user to a book they favorited; favorites are per user |
| **Rating** | A user's rating of a book; ratings are per user |
| **UserLibrary** | Links a user to a book in their personal library (borrowed books) |

Relationships at a glance:

```text
User 1 ──── * Favorite * ──── 1 Book
User 1 ──── * Rating   * ──── 1 Book
User 1 ──── * UserLibrary * ── 1 Book
```

## Contributing

Contributions are welcome. This section describes the standard fork → branch → commit → push → pull request workflow.

### Fork and Clone

1. Fork the repository on GitHub.
2. Clone your fork and add the original as `upstream`:

```bash
git clone https://github.com/YOUR_USERNAME/book-library-manager.git
cd book-library-manager
git remote add upstream https://github.com/ORIGINAL_OWNER/book-library-manager.git
```

3. Set up your environment by following [Installation](#installation).

### Create a Branch

```bash
git checkout main
git pull upstream main
git checkout -b feature/your-feature-name
```

Use descriptive prefixes such as `feature/`, `fix/` or `docs/`.

### Development Guidelines

- Keep frontend and backend responsibilities separate.
- Validate user input on both sides; keep backend validation authoritative.
- Preserve existing authentication and authorization behavior.
- Use environment variables for secrets and configuration; avoid hard-coded credentials.
- Keep reusable React components reusable.
- Keep API behavior documented (see [API Documentation](#api-documentation)).
- Follow the existing project structure and code style.
- Keep changes focused; avoid unrelated formatting or refactoring in feature PRs.
- **Do not commit** secrets, `.env`, `venv/` or `node_modules/`.
- Test backend and frontend changes locally before submitting.
- Update the API documentation when you change an API, and the README when you add major functionality.

### Commit Changes

```bash
git add .
git commit -m "Add book search functionality"
git push origin feature/your-feature-name
```

Write clear, imperative commit messages that describe what changed.

### Pull Request

1. On GitHub, open a Pull Request from your branch to the `main` branch of the main repository.
2. Explain **what** changed and **why**, how you tested it, and link any related issue.
3. Call out breaking changes explicitly.
4. Include screenshots for UI changes.
5. Wait for review and address requested changes by pushing more commits to the same branch.

### Bug Reports

Open an issue and check first that it has not already been reported. A useful report includes:

- **Description:** what went wrong
- **Steps to reproduce:** numbered, minimal steps
- **Expected behavior**
- **Actual behavior**
- **Environment:** OS, Python and Node versions, browser, and whether you used Docker
- **Screenshots or logs**, if useful (remove any secrets)

### Feature Requests

Search existing issues first to avoid duplicates. If none matches, open a new issue describing the problem, your proposed solution, and any alternatives you considered. Discuss larger changes in the issue before starting work.
